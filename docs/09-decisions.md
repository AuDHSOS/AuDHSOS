# 9. Decision Register

Every binding decision as a statement. A decision is changed by a new entry
that supersedes the old one; entries are never edited after acceptance.

Status values: `decided` (stated by the project owner), `proposed`
(awaiting confirmation), `superseded by D-nn`.

| ID | Decision | Status | Date |
|----|----------|--------|------|
| D-01 | AuDHSOS is a microkernel. The kernel provides address spaces, threads with scheduling, IPC, capabilities, and interrupt forwarding, and nothing else. | decided | 2026-09-04 |
| D-02 | Everything else runs in userland: drivers including the console driver, program loading, naming, memory policy, fault handling, file systems, networking. | decided | 2026-09-04 |
| D-03 | The system is written in Rust. No assembly files, no `global_asm!`. Inline assembly only in adapter crates, inventoried and budgeted. Memory management contains no assembly. | decided | 2026-09-04 |
| D-04 | No external code. `Cargo.lock` lists only workspace members. No crates.io, git, or vendored third-party code in any dependency section, including build and dev dependencies. No external Cargo subcommands. The only external components are the Rust toolchain and QEMU with its bundled UEFI firmware. | decided | 2026-09-04 |
| D-05 | `unsafe` is confined to the allowlisted adapter crates `kernel-hal-x86_64`, `boot-uefi-x86_64`, `audhsos-sync`, `user-sys-x86_64`, and `fuzz-support`. Every other crate has `#![forbid(unsafe_code)]`. Every `unsafe` block has a `SAFETY:` comment and counts against a budget checked in CI. | decided | 2026-09-04 |
| D-06 | Every algorithm is written against a trait and tested on the host with doubles. Adapters implement the traits for the loader and the kernel. One implementation per algorithm. | decided | 2026-09-04 |
| D-07 | First target: QEMU `q35` on `x86_64`, booted through UEFI. Legacy BIOS boot is not supported. Second target: `aarch64` on QEMU `virt` under HVF. Third target: `riscv64` on QEMU `virt`. | decided | 2026-09-04 |
| D-08 | The loader is the project's own UEFI application `boot-uefi-x86_64`. UEFI structure layouts live in the logic crate `audhsos-uefi`. The loader reads `AUDHSOS/KERNEL.ELF` and `AUDHSOS/BOOT.IMG` from the boot volume, builds page tables with the kernel's mapper, and enters the kernel with the boot information structure. | decided | 2026-09-04 |
| D-09 | The disk image is written by the xtask: GPT with a protective MBR and one EFI system partition, FAT32 only, 8.3 names, no long file name entries. | decided | 2026-09-04 |
| D-10 | The toolchain is one pinned nightly. Unstable features: `abi_x86_interrupt`, `custom_test_frameworks`, `-Zsanitizer=fuzzer` on the host. Adding a feature requires a register entry. | decided | 2026-09-04 |
| D-11 | The kernel has no heap and does not link `alloc`. Kernel objects live in typed pools sized at boot from the kernel reserve, addressed by generation-checked ids. Every allocation is fallible. Each process has a kernel-object quota. | decided | 2026-09-04 |
| D-12 | The kernel allocates user memory never after boot. All free memory becomes memory objects of the root task; memory objects are split, never merged, by the kernel. The memory server overwrites every memory object with zeros before handing it out and again immediately when it is returned. | decided | 2026-09-04 |
| D-13 | Capabilities: per-process handle tables with generation-checked handles, rights that only decrease, badges on endpoint capabilities, no recursive revocation in the first release. A handle is 64 bits: 32-bit table index, 32-bit generation. | decided | 2026-09-04 |
| D-14 | IPC: synchronous rendezvous on endpoints (`call`, `send`, `recv`, `reply`, `reply_recv`, `try_recv`) plus notifications with 64 signal bits. Messages carry up to 480 words and 4 handles through IPC buffers. Bulk data uses shared memory objects. | decided | 2026-09-04 |
| D-15 | System calls enter through interrupt vector `0x80` with the `x86-interrupt` ABI. Arguments and results live in the calling thread's IPC buffer. No user pointers in the interface. The system call table is one declarative macro in `audhsos-abi`. The `syscall` instruction path is decided in Phase 8 by measurement. | decided | 2026-09-04 |
| D-16 | Faults in user mode become IPC calls to the process's fault handler endpoint. | decided | 2026-09-04 |
| D-17 | The kernel is non-preemptible and runs on one CPU in the first release. System calls are bounded and return `Partial` for range operations. The SMP path is per-CPU run queues and a big kernel lock first. | decided | 2026-09-04 |
| D-18 | Scheduling: 32 fixed priorities, FIFO run queue per priority, round-robin time slices in timer ticks, idle thread on the boot stack. | decided | 2026-09-04 |
| D-19 | I/O port access from userland is a system call on an `IoPortRange` handle. Userland drivers contain no inline assembly. | decided | 2026-09-04 |
| D-20 | Allocators compute offsets, not pointers. The frame allocator and the userland heap allocator are project code in safe Rust; the only `unsafe` is the `GlobalAlloc` adapter in `user-sys-x86_64`. | decided | 2026-09-04 |
| D-21 | Global state uses `audhsos-sync::Global<T>` with a runtime borrow flag. No spinlock crate. | decided | 2026-09-04 |
| D-22 | The ELF parser `audhsos-elf` and the UART register logic `driver-uart16550` are single logic crates shared by loader, kernel, and userland. | decided | 2026-09-04 |
| D-23 | Testing: logic on the host with the project's property-test engine and model-test runner; adapters in QEMU with the custom test framework, the serial protocol, and `isa-debug-exit`; parsers fuzzed with the toolchain's sanitizer runtime; coverage with the toolchain's `llvm-profdata` and `llvm-cov`. The edge-case catalog is the definition of done. | decided | 2026-09-04 |
| D-24 | Policies (layering, unsafe budgets, SPDX header, fuzz targets) are Rust tables in `xtask/src/policy.rs`. No configuration file parsers. | decided | 2026-09-04 |
| D-25 | License `AGPL-3.0-only` without exceptions, SPDX header in every file, copyright line `Copyright (C) 2026 Manuel Baesler and contributors`. | decided | 2026-09-04 |
| D-26 | Everything is written in English: code, comments, documentation, commits, tests. | decided | 2026-09-04 |
| D-27 | The boot image is a fixed header, the root task as a flat binary at `ROOT_TASK_BASE`, and a ustar tar archive. The kernel validates the header and never reads the archive. | decided | 2026-09-04 |
| D-28 | The boot information structure is `#[repr(C)]` in `audhsos-abi`, versioned, with a bounded region array. | decided | 2026-09-04 |
| D-29 | Graphics output and input devices are in scope after release 0.1.0 as Phases 9 to 11 of the roadmap. Sound stays out of scope. | decided | 2026-09-05 |
| D-30 | Graphics output is the linear framebuffer that the UEFI Graphics Output Protocol reports. The loader reads the mode the firmware has set and does not change it. The boot information carries the framebuffer description; the root task creates a `Device` memory object for it and hands it to a userland display server. No virtio-gpu in the first graphics release. | decided | 2026-09-05 |
| D-31 | Input devices are the PS/2 keyboard and mouse behind the i8042 controller, driven by a userland input driver through `IoPortRange` and `Interrupt` capabilities. Events reach clients through a ring buffer in a shared memory object plus a notification, never through one IPC call per event. | decided | 2026-09-05 |
| D-32 | The boot information structure carries the framebuffer fields from Phase 2 on. Version 1 is extended, not bumped, because no image with the old layout has been released. An absent framebuffer is reported with every framebuffer field zero. | decided | 2026-09-05 |
| D-33 | Graphical tests drive QEMU through QMP from the xtask: input events are injected with `input-send-event`, the screen is read with `screendump`. The xtask contains its own JSON subset and PPM reader. CI runs without a display window. | decided | 2026-09-05 |
| D-34 | The project name is `AuDHSOS`; the crate prefix is `audhsos`. | decided | 2026-09-05 |
| D-35 | The build entry point on the development machine is rustup's Cargo proxy, `~/.cargo/bin/cargo xtask ...`. The xtask refuses to run under any other Cargo, including the shell alias. | decided | 2026-09-05 |
| D-36 | HTTPS support is prepared as a self-contained track of logic crates: `crypto-ct`, `crypto-hash`, `crypto-aead`, `crypto-ec`, `crypto-rng`, `audhsos-der`, `audhsos-x509`, `audhsos-tls`. They perform no I/O and no allocation, are host-tested, and are built independently of the kernel phases. The design is document 11. | decided | 2026-09-05 |
| D-37 | The first version is a TLS 1.3 client only (RFC 8446). No TLS 1.2 or earlier, no server role, no session resumption, no pre-shared keys, no 0-RTT, no client certificates, no renegotiation, no DTLS. | decided | 2026-09-05 |
| D-38 | Algorithms of the first version: cipher suites `TLS_AES_128_GCM_SHA256`, `TLS_AES_256_GCM_SHA384`, `TLS_CHACHA20_POLY1305_SHA256`; key exchange `x25519` and `secp256r1`; signature verification `ecdsa_secp256r1_sha256`, `ecdsa_secp256r1_sha384`, `ed25519`. RSA verification and the bignum crate it needs are later work. | superseded in part by D-56 | 2026-09-05 |
| D-39 | Symmetric primitives are constant-time by construction: bitsliced AES without lookup tables, GHASH without tables, no branch and no index on a secret value anywhere. The asymmetric product surface is verification only; signing exists solely behind test features. Each crate documents which functions see secrets and why their control flow is on public data. | decided | 2026-09-05 |
| D-40 | Test vectors transcribed from RFCs and NIST publications into Rust source files are specification data, not external code under R8; each table names its source. Certificates, keys, and chains used in tests are generated by project code behind test features, never vendored. | decided | 2026-09-05 |
| D-41 | The TLS library is sans-I/O. The caller supplies the buffers and the transport; the library exposes `read_tls`, `write_tls`, `poll`, `send`, `recv`, `close` and allocates nothing. | decided | 2026-09-05 |
| D-42 | The repository contains no certificate trust anchors. Anchors are an operator-supplied build input that the xtask converts into a DER table for the boot image; `audhsos-x509` takes them as a parameter. | decided | 2026-09-05 |
| D-43 | Randomness is the `Entropy` trait plus the `ChaChaRng` generator in `crypto-rng`. The platform source is `RDSEED` in `kernel-hal-x86_64` behind a `random_bytes` system call and is specified when the network stack is scheduled; until then no product code constructs a generator. | decided | 2026-09-05 |
| D-44 | Certificate validation covers the RFC 5280 subset stated in document 11 plus RFC 6125 name matching against `dNSName` entries. Revocation checking and name constraints are not implemented in the first version and are documented limits. | decided | 2026-09-05 |
| D-45 | Work parallel to the kernel phases is admitted only for crates that pass the admission test of document 12: pure logic without I/O, the lint profile of a logic crate, no dependency on kernel, loader, or userland crates, and a catalog entry that can be written and tested on the host today. At most one side track besides the cryptography track is active at a time, and a track is worked on between phases, never instead of one. | decided | 2026-09-05 |
| D-46 | Time is a crate: `audhsos-time` owns `UnixTime`, `CivilTime`, `Instant`, and `Duration`. `audhsos-der` imports `UnixTime` instead of defining it, which amends document 11 section 11.9. No crate of the project reads a clock; time enters every interface as a parameter. | decided | 2026-09-05 |
| D-47 | Base64, hex, and PEM live in `audhsos-encoding` at layer 0. The trust-anchor conversion of D-42 and the test certificate builder use it; the xtask contains no second decoder. | decided | 2026-09-05 |
| D-48 | `audhsos-collections` provides fixed-capacity, index-based containers without `unsafe` and without allocation: `ArrayVec`, `RingBuffer`, `BitSet`, `IndexList`, `IndexMap`. Kernel run queues, endpoint wait queues, and the network stack use them instead of an index scheme written per crate. | decided | 2026-09-05 |
| D-49 | The network stack is a track of sans-I/O logic crates: `net-wire`, `net-eth`, `net-ip`, `net-udp`, `net-tcp`, `net-dns`, `net-dhcp`, `net-http`, `net-stack`. They perform no I/O and no allocation, take time and randomness as parameters, and are host-tested. The design is document 12. The virtio-net driver, the network server, the socket protocol, and the entropy system call are integration and stay unscheduled. | decided | 2026-09-05 |
| D-50 | Scope of the first network version: IPv4 only, no IPv6; Ethernet II without VLAN tags; TCP options limited to the maximum segment size, so no window scaling, no selective acknowledgment, and no timestamps; Reno congestion control; no IP forwarding and no multicast beyond what ARP and DHCP need; HTTP/1.1 without content encodings and without following redirects. | decided | 2026-09-05 |
| D-51 | TCP draws its initial sequence numbers, UDP its ephemeral source ports, and DNS and DHCP their transaction ids, from the `Rng` trait of `crypto-rng`. This is the only dependency edge from the network track into the cryptography track; `audhsos-tls` and the network crates never reference each other. | decided | 2026-09-05 |
| D-52 | `virtio-queue` implements the split virtqueue of virtio 1.x and the device initialization state machine over a memory access trait, with no register access in the crate. No packed rings, no indirect descriptors, and no `EVENT_IDX` in the first version. | decided | 2026-09-05 |
| D-53 | The FAT32 structural logic moves from the xtask into `fs-fat` over a `BlockDevice` trait; the image writer becomes a user of that crate, as does a later file system server. FAT32 only with 8.3 names, unchanged from D-09; timestamps go through `audhsos-time`. | decided | 2026-09-05 |
| D-54 | `fuzz-support` provides the fuzzer entry glue, the `fuzz_target!` macro, and the regression corpus handling for every fuzz target in the catalog. `audhsos-symbols` resolves an address to function, file, and line from an ELF symbol table and a DWARF line program of version 4 or 5; the xtask uses it for panic addresses. No inline frames and no stack unwinding in the first version. | decided | 2026-09-05 |
| D-55 | The kernel binary `audhsos-kernel` is an allowlisted adapter crate. Its `unsafe` is the entry the loader jumps to, the panic handler, the reads of the window during the memory bring-up, and the same in the test images it carries. This amends D-05, which named the crate nowhere although the crate has held `unsafe` since Phase 2. | decided | 2026-09-05 |
| D-56 | The key exchange of the TLS 1.3 client is `x25519` alone; this supersedes the key exchange named in D-38. A key exchange multiplies a secret scalar, and the P-256 of `crypto-ec` is a verification implementation whose branches follow public values by design. Offering `secp256r1` would need a second scalar multiplication written to the constant-time discipline, in a module whose clarity comes from not needing one. X25519 is mandatory to implement in RFC 8446, so a client that offers it alone reaches every conforming server; the cost is servers that accept P-256 only. Signature verification over P-256 is unaffected and stays in scope. | decided | 2026-09-05 |
| D-57 | The object pools live in the `.bss` of the kernel image as `static` cells, not in the kernel reserve: a `Pool<T, N>` is a typed array, and putting one into raw frames would need `unsafe` in a logic crate. This amends 2.4.1, which said the reserve holds them. The reserve holds what the count of is not known before boot: page tables, kernel stacks, and IPC buffers. The numbers follow from that: `THREADS` and `KERNEL_STACKS` are 256, because every thread costs five frames of the reserve and 1024 of them do not fit the reserve of the reference machine; `PROCESSES` is 64 and `HANDLES_PER_PROCESS` is 1024, because the handle table lives in the `Process` object and 256 tables of `1 << 16` entries would be hundreds of mebibytes of `.bss`. The reference machine keeps its 256 MiB. | decided | 2026-09-05 |
| D-58 | The handle slots of the machine are one `static` arena of `HANDLE_ENTRIES` (16384, two per kernel object the machine can hold), and a process holds a `HandleList` of what it has and what its creator granted it. `HANDLES_PER_PROCESS` (4096) becomes the ceiling the quota enforces against that arena instead of memory set aside per process; this supersedes the handle part of D-57, which put a table of 1024 entries inside every `Process`. The demand that decides the number is `server-memory`, which holds one handle per memory object it hands out and can therefore reach `MEMORY_OBJECTS`; 1024 was too few for it and 4096 inline would have been 8 MiB of `.bss` for one process that needs it. A slot names its owner, and a lookup checks the owner as well as the generation. This is what 2.3.2 already required of a handle table: a capacity fixed at process creation within the creator's quota. | decided | 2026-09-05 |
| D-59 | The standards this system implements are kept verbatim under `docs/rfc/`, with their source, the date they were retrieved, and a checksum recorded beside them. They are documents: nothing there is compiled, linked, or read at run time, so rule R8 is untouched, and they are not covered by this repository's licence. A test vector is still transcribed into Rust source with its document and section named, as D-40 requires; the file is there so that the transcription can be checked without a network and so that the source cannot change under a test that cites it. | decided | 2026-09-05 |
| D-60 | The physical window covers memory, and the kernel maps the device apertures it needs into it itself. The loader sizes the window from the memory map, because a window over the whole address space of the reference machine would be a terabyte of page tables; a device the kernel drives, which in this release is the local APIC and the I/O APICs, is therefore mapped by the memory bring-up at `PHYS_WINDOW_BASE + address`, uncached, and registered as a region of kind `Device`. One rule reaches all of physical space, and the tables that reach the apertures are the kernel's own. This states what 4.6 left open when it said the adapter obtains the APIC register block through the window. | decided | 2026-09-05 |
| D-62 | A trust anchor is a subject and a key, and `TrustAnchor::from_certificate` reads a certificate no further than its key: the certificate's own signature is never verified, nor is its window, its authority bit, or its key usage. A self-signature says nothing about whether a root should be trusted, since the party that signed it is the party being judged, and requiring one to be readable would rule out the certificates that carry an anchor's key without being self-signed — a root cross-signed by an older authority is signed with that authority's algorithm, which may be one this system has no arithmetic for. `GTS Root R4` in the chain `google.de` presents is such a certificate, signed by GlobalSign with RSA. What is checked is that the bytes are a certificate as far as the key and that the key is one this system can verify with, so that an unusable anchor is refused where the caller still holds the file rather than becoming a path that reaches nothing. 11.9 already gives the type as a subject and a key; this states what follows when one is read out of a certificate, which `verify_chain` assumed and nothing offered. | decided | 2026-09-05 |
